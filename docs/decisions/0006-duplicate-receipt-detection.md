# 6. กันแต้มซ้ำด้วยหลายสัญญาณ + ตาราง receipts

สถานะ: Accepted

## บริบท

ก่อนหน้านี้ระบบ **ไม่เคยจำว่ารับใบเสร็จใบไหนไปแล้ว** — ไม่มีตาราง `receipts`
และ `receipt_check/duplicate_check.py` เป็นไฟล์เปล่า
ผลคือลูกค้าถ่ายใบเสร็จใบเดิมส่งซ้ำได้แต้มทุกครั้งที่ส่ง

สิ่งที่มีอยู่คือ `receipt_fingerprint(ร้าน + เลขที่ + วันที่ + ยอด)` ซึ่งถูกส่งเป็น
`reference` ให้ loga โดยหวังพึ่ง idempotency ฝั่งเขา (ADR 0003 #7)

**แต่ลายนิ้วมือนั้นใช้ไม่ได้จริง** — วัดกับใบเสร็จจริง 28 รูปแล้วพบว่า
ชื่อร้านที่ OCR อ่านได้ไม่คงที่ระหว่างรูปของใบเดียวกัน:

```
ใบ KFC 149 บาท ใบเดียวกัน
  รูป #1  → "CRG-KFC 12IO2 (KEC-BIO C NAKORNSAVAN)"
  รูป #28 → "2330 Host: Prapapan #2330 BOX AI1 Easy"   ← ไม่ใช่ชื่อร้านด้วยซ้ำ
```
→ ลายนิ้วมือคนละค่า → loga มองเป็นคนละรายการ → **ได้แต้มสองเท่า**

## สิ่งที่ค้นพบตอนทำเฉลยของชุดทดสอบ

รูป 28 ใบไม่ใช่ใบเสร็จ 28 ใบ แต่เป็น **การซื้อ 12 ครั้ง · กระดาษ 14 ใบ · ถ่ายใบละ 2 มุม**
ทำให้ได้ชุดทดสอบการกันซ้ำที่มีเฉลยครบ และเจอ 3 เรื่องที่แฮชค่าเดียวแก้ไม่ได้:

| # | สถานการณ์ | ทำไมแฮชแก้ไม่ได้ |
|---|---|---|
| 1 | รูปคนละมุมของใบเดียวกัน OCR อ่านได้ไม่เท่ากัน (ใบ DQ รูปหนึ่งหัวใบหลุดเฟรม ไม่มีเลขใบกำกับเลย) | ค่าที่เอาไปแฮชไม่เท่ากัน |
| 2 | การซื้อครั้งเดียวมีกระดาษ 2 ใบ (ใบเสร็จร้าน + สลิปบัตร) เลขอ้างอิงไม่ตรงกันสักตัว | ไม่มีค่าร่วมให้แฮช |
| 3 | คนละใบจริงๆ ที่ ร้าน/วัน/ยอด เหมือนกันหมด (DQ 79 บาท 2 ใบ ห่างกัน 38 นาที) | แฮชเท่ากันทั้งที่คนละใบ |

## การตัดสินใจ

### 1. เพิ่มตาราง `receipts` (migration 0002)
เก็บทุกใบที่ระบบรับไว้ พร้อมสถานะ (`PENDING` / `AWARDED` / `FAILED` / `REJECTED`)
— ไม่มีตารางนี้ก็ไม่มีอะไรให้เทียบ กันซ้ำไม่ได้เลย

### 2. ตัดสินด้วยกฎเรียงตามความมั่นใจ ไม่ใช่แฮชค่าเดียว
(`receipt_check/duplicate_check.py`)

```
กฎ 0  ยอดต่างกัน                     → ไม่ซ้ำ   (ยอดคือ field ที่แม่นที่สุด 96%)
กฎ 1  แชร์เลขอ้างอิง ≥ 1 ตัว          → ซ้ำ      (ข้ามสมาชิกได้ — กระดาษใบเดียวแลกได้ครั้งเดียว)
กฎ 2  วันที่ห่างกันเกิน 1 วัน          → ไม่ซ้ำ
กฎ 3  เวลาห่างกันเกิน 15 นาที         → ไม่ซ้ำ
กฎ 4  นอกนั้น                        → ซ้ำ      (ฝั่งปลอดภัย)
```

ค่าคงที่ทั้งสองตัวมาจากของจริง ไม่ได้ตั้งลอยๆ:
- **15 นาที** — ต้องมากกว่าระยะใบเสร็จ↔สลิปของการซื้อเดียวกัน (8-14 วินาที)
  และน้อยกว่าระยะ DQ 2 ใบที่เป็นคนละการซื้อจริง (38 นาที)
- **±1 วัน** — เพราะ OCR อ่านวันที่ผิดได้จริง (ใบ #13 อ่าน 06/06/2026 เป็น 05/05/2026)
  ถ้าเชื่อวันที่แบบตรงเป๊ะ ใบซ้ำที่อ่านวันเพี้ยนจะหลุดผ่าน

กฎ 1 ใช้ข้ามสมาชิกทั้ง tenant ส่วนกฎ 2-4 จำกัดแค่สมาชิกคนเดียวกัน
เพราะกฎ 2-4 อ่อนพอที่คนละคนจะชนกันได้เองในร้านอาหารช่วงพีค

### 3. เลขอ้างอิงต้องมี "ป้ายกำกับ" เท่านั้น
(`receipt_data/reference_code.py`)

เก็บเฉพาะเลขที่ตามหลังป้ายของธุรกรรม (`Invoice ID` / `TRANS ID` / `Tax INV` /
`TRACE#` / `STAN#` / `APPR`) — **ห้ามเก็บเลขยาวๆ ทุกตัวบนใบเสร็จ**
เพราะจะไปโดน `TAX ID` (เลขผู้เสียภาษีของร้าน), `POS ID` (เครื่องแคชเชียร์),
`MER#` (รหัสร้านฝั่งธนาคาร) ซึ่งเหมือนกันทุกใบของร้านนั้น
→ ลูกค้าซื้อ KFC 149 บาทสองวันติดจะถูกมองเป็นใบเดียวกัน แล้วเสียแต้มของวันที่สอง

เป้าหมายคือ "อ่านได้ค่าเดิมทุกครั้ง" ไม่ใช่ "อ่านได้ถูกต้อง" —
เลขที่อ่านเพี้ยนเหมือนกันทั้งสองรูปก็ใช้กันซ้ำได้ผลเท่ากัน

### 4. `reference` ที่ส่งให้ CRM = id ของแถวในตาราง `receipts` ไม่ใช่แฮชเนื้อหา
เปลี่ยนจาก ADR 0003 #7 ("ใช้เลขที่ใบเสร็จเป็น reference") โดยตั้งใจ

เหตุผล: loga ถือว่า reference ซ้ำ = รายการเดิม เราจึงอยากให้มันซ้ำ
"เมื่อเป็นแถวเดิมเท่านั้น" ไม่ใช่ซ้ำเพราะเนื้อหาบังเอิญคล้ายกัน
การตัดสินว่าซ้ำหรือไม่เป็นหน้าที่ของ `duplicate_check` ซึ่งฉลาดกว่าการเทียบแฮช
ส่วน idempotency ฝั่ง CRM เหลือหน้าที่เดียวคือกันการยิงซ้ำจาก retry ของเราเอง

### 5. ลำดับในงานสแกน: กันซ้ำ → บันทึกแถว (commit) → ส่งแต้ม
บันทึกและ **commit ก่อน** ส่งแต้มเสมอ
ถ้าบันทึกทีหลัง ช่วงที่ระบบพังพอดีจะไม่มีร่องรอยว่าเคยให้แต้มใบนี้ไปแล้ว

แถวที่ส่งแต้มไม่สำเร็จถูกทำเครื่องหมายเป็น `FAILED` และ **ถูกใช้ซ้ำ** เมื่อลูกค้าส่งใหม่
(ด้วย reference เดิม) — ไม่ใช่ถูกบล็อกว่า "ใบซ้ำ" ไม่งั้นลูกค้าจะไม่มีวันได้แต้มของใบนั้นเลย

## ทางเลือกที่ไม่เลือก

| ทางเลือก | ทำไมไม่เลือก |
|---|---|
| แฮชเนื้อหาแล้วเทียบตรงเป๊ะอย่างเดียว | แก้ 3 สถานการณ์ข้างบนไม่ได้เลย — พิสูจน์แล้วด้วยของจริง |
| ให้คะแนนแต่ละสัญญาณแล้วตั้ง threshold | อธิบายกับคนไม่ได้ว่าทำไมใบนี้ถูกปฏิเสธ · ปรับจูนแล้วไม่รู้ว่าดีขึ้นตรงไหน |
| เก็บเลขอ้างอิงเป็นตารางลูกแยก | คิวรีจริงกรองด้วย tenant+ยอดก่อนเสมอ เหลือไม่กี่แถว เทียบในหน่วยความจำเร็วพอ |
| แฮชรูปด้วย perceptual hash (pHash) | ถ่ายคนละมุม/คนละแสง ค่าต่างกันมาก · และไม่ช่วยเคสใบเสร็จคู่กับสลิป |

## ผลที่วัดได้

วัดด้วย `python -m app.tools.measure_duplicate` กับใบเสร็จจริง 28 รูป:

```
ใบซ้ำที่จับได้    15/15
★ ใบซ้ำที่หลุด    0/15     ← ให้แต้มซ้ำ
จับเกิน           0/12     ← ลูกค้าเสียแต้มที่ควรได้
```

รวมทั้งสองเคสยาก: ใบเสร็จ↔สลิปของการซื้อเดียวกันถูกจับว่าซ้ำ
และ DQ 79 บาท 2 ใบที่ห่างกัน 38 นาทีไม่ถูกจับ

## ความเสี่ยงที่ยังเหลือ

- **อ่านเลขอ้างอิงได้แค่ 7/14 เอกสาร** ที่เหลือพึ่งกฎ 2-4 ซึ่งอ่อนกว่า
  → ปรับปรุงได้เมื่อมี template ต่อร้าน (Step 5)
- **อ่านเวลาได้ 21/28** ใบที่อ่านเวลาไม่ได้จะตกไปที่กฎ 4 (ถือว่าซ้ำ)
  = ฝั่งปลอดภัย แต่ลูกค้าที่ซื้อซ้ำจริงอาจถูกบล็อก
- **ชื่อรายการสินค้ายังไม่ถูกใช้เป็นสัญญาณ** ทั้งที่เป็นตัวแยก DQ 2 ใบได้ชัดที่สุด
  (`CONE(L)+BZ OVL MINT CHIP` vs `BG BZ FERRERO S`) → รอการอ่านรายการสินค้า
