# 3. ข้อจำกัดจริงของ loga API และผลต่อการออกแบบ

สถานะ: Accepted

## บริบท

เดิมเรามีแต่ Swagger (`docs/Loga_API_Document.txt`) ซึ่งบอก **พารามิเตอร์** แต่ไม่บอก
**พฤติกรรม** ทำให้ต้องเขียนโค้ดบนสมมติฐาน ต่อมาได้ Loga API Integration Guidelines
(https://blog.loga.app/loga-api-integration-guidelines/) ซึ่งยืนยัน/หักล้างสมมติฐานได้หลายข้อ

## สิ่งที่ยืนยันแล้ว + ผลต่อโค้ด

| # | ข้อเท็จจริง | ผลต่อโค้ด |
|---|---|---|
| 1 | **สำเร็จ = `code` 200** ไม่ใช่ 0 | `SUCCESS_CODE = 200` ใน `loga_token.py` — เดิมเขียน 0 ตามค่า placeholder ของ Swagger ซึ่งผิด |
| 2 | token **ไม่มีวันหมดอายุ** แต่ตายเมื่อ logout หรือเปลี่ยนรหัสผ่านผ่านเว็บ | ต่ออายุล่วงหน้าไม่ได้ → ตั้งรับด้วย `refresh_token(stale)` เท่านั้น |
| 3 | logout ฆ่า token | **ห้ามเขียนเมธอด logout** ระบบเราไม่มีเหตุผลต้องใช้ และเผลอเรียกครั้งเดียว = ทุก process ตายพร้อมกัน |
| 4 | `uuid` เป็น string อะไรก็ได้ แต่ต้อง **คงที่ตลอดไป** และใช้คู่กับ token ที่ขอด้วย uuid นั้น | เป็น config `LOGA_DEVICE_ID` ห้ามสุ่มตอน runtime · เปลี่ยนค่า = token เดิมใช้ไม่ได้ |
| 5 | `card_id` required เกือบทุก endpoint | เป็น config `LOGA_CARD_ID` ไม่ใช่ค่าที่ส่งมาจากชั้นธุรกิจ |
| 6 | loga **ห้ามสมัครซ้ำ** ด้วยเบอร์ที่มีอยู่แล้ว และแนะนำให้ `get_customer_info` ก่อนเสมอ | `member_link.py` ต้องเป็น "หาก่อน → ไม่เจอค่อยสมัคร" ไม่ใช่ "สมัครแล้วดักพัง" |
| 7 | `reference` ซ้ำ = loga ถือเป็นรายการเดิม ไม่บันทึกซ้ำ | ได้ idempotency ของการให้แต้มฟรีจากฝั่ง loga ใช้เลขที่ใบเสร็จเป็น `reference` |
| 8 | `replace_duplicate=yes` เขียนทับรายการเดิมได้ | ช่องทางแก้แต้มที่ให้ผิด โดยไม่ต้องสร้างรายการใหม่ |
| 9 | `formula_id` ดึงได้จาก `get_card_detail` → `data.point_product.add[0].formula_id` | ไม่ต้อง hardcode · card detail แทบไม่เปลี่ยน → cache ได้ยาว |
| 10 | `cost` + `formula_id` ให้ loga คิดแต้ม (ยืนยันแบบ B ใช้ได้จริง) | ตามที่ตัดสินใจไว้ใน ADR 0002 ไม่ต้องเปลี่ยน |

## ผลต่อความเสี่ยงของ Step 1

ข้อ 1 คือเซอร์ไพรส์ที่ Step 1 ตั้งใจจะเจอ — ถ้าไม่รู้ ระบบจะมองว่า **login ที่สำเร็จจริงคือ
login ที่พัง ทุกครั้งโดยไม่มีข้อยกเว้น** และอาการจะไปโผล่ตอนต่อระบบจริงซึ่งหาสาเหตุยากกว่ามาก

## ยังไม่ตัดสินใจ (ต้องเคลียร์ก่อน Step 2)

**สมาชิกที่เราสร้างให้ จะเป็นสมาชิกประเภทไหน**
`subscribe_by_unregistered_card` สร้าง "สมาชิกบัตรพลาสติก" คืน `data.pcard_id` — ไม่ใช่
สมาชิกออนไลน์ที่มี `uid` ทั้งที่ลูกค้าเราสมัครผ่าน LINE

ทางเลือก: (ก) ใช้ `pcard_id` แล้วให้แต้มด้วย `cuid = "P" + pcard_id` (loga รองรับทางลัดนี้)
(ข) หาวิธีให้ลูกค้าเป็นสมาชิกออนไลน์ผ่าน LINE ของ loga เอง

กระทบทั้ง `member_link.py` และรูปแบบข้อมูลที่เก็บใน `members` — ตัดสินตอน Step 2

## ⚠ เอกสารสองฉบับขัดกันเอง: รหัสสมาชิกอยู่ตรงไหน

| แหล่ง | บอกว่ารหัสสมาชิกอยู่ที่ |
|---|---|
| Swagger (`Loga_API_Document.txt`) | `data.user_info.uid` (และ `data.card` มีแค่ `created`/`expired`) |
| Integration Guidelines | `data.card.uid` |

เลือกข้างไม่ได้เพราะยังยิงของจริงไม่ได้ และเดาผิด = **หาสมาชิกไม่เจอทุกคน** ทั้งระบบ

**ทางออกชั่วคราว:** `loga_client._to_customer()` อ่านทั้งสองที่ แล้วตัดข้างที่ผิดทิ้ง
เมื่อเห็นคำตอบจริงครั้งแรก — ยอมรับความคลุมเครือชั่วคราว ดีกว่าเดาแล้วพังเงียบ

## สมมติฐานที่ยังต้องยืนยันด้วยการยิงจริง

- `code` ค่าไหนหมายถึง "token ใช้ไม่ได้" (เอกสารทั้งสองฉบับไม่ระบุ code ของ error เลย)
  → ตอนนี้เดาเป็น `{401, 403}` ใน `loga_client.AUTH_ERROR_CODES`
- `code` ค่าไหนหมายถึง "ไม่พบสมาชิก" → ตอนนี้ถือว่าทุก code ที่ไม่สำเร็จคือไม่พบ
- login ซ้ำด้วย `uuid` เดิม จะเตะ token เก่าทิ้งหรือได้ token ที่ใช้พร้อมกันได้หลายตัว
  (ความสำคัญลดลงมาก เพราะ token ไม่มีวันหมดอายุ การ login ซ้ำจึงแทบไม่เกิด)
