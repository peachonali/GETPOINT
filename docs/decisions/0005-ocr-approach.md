# 5. แนวทาง OCR: PaddleOCR + OpenCV เตรียมรูป (ไม่เทรนโมเดลเอง)

สถานะ: Accepted

## บริบท
ต้องอ่าน "ยอดเงิน" จากใบเสร็จไทยให้แม่น เพราะอ่านผิด = ลูกค้าได้แต้มผิด
ซึ่งเป็นความเสียหายที่ดึงคืนยากที่สุด

## ตัดสินใจ
1. **ใช้ PaddleOCR (โมเดล `th_PP-OCRv5`) รันบนเครื่องเรา** — ไม่เทรนโมเดลใหม่
2. **ลงแรงที่ "เตรียมรูป" (OpenCV) แทนการเทรน** — ตัดขอบ → ดัดเอียง → ปรับ contrast
3. **Gemini เป็นตัวสำรองสำหรับร้านใหม่เท่านั้น** (Step 5) ไม่ใช่ตัวอ่านหลัก

## เหตุผล
- **เทรนเองไม่คุ้ม**: ต้องมีใบเสร็จติดป้ายกำกับหลักพัน-หมื่นใบ + GPU หลายวัน
  ขัดกับข้อตกลงที่ตัด GPU ออก (blueprint ส่วนที่ 3)
- **ต้นทุนต่อใบ = 0**: cloud OCR คิดเงินทุกครั้ง · ของเรารันเองไม่มีค่าใช้จ่ายผันแปร
- **PDPA**: ใบเสร็จไม่ต้องออกนอกระบบเรา
- **สิ่งที่ต้องอ่านคือ "ตัวเลข" ไม่ใช่ภาษาไทยทั้งใบ** — ง่ายกว่ามาก

## วัดผลจริง (ใบเสร็จจริง 28 ใบ + สังเคราะห์ 1)
| จุด | ผล |
|---|---|
| เตรียมรูปก่อน OCR (รูปเอียง 6°) | อ่านได้ 5/6 บรรทัด → **6/6** และเร็วขึ้น 42% (2.88s → 1.67s) |
| อ่านยอดได้ (ก่อนแก้บั๊ก) | 1/29 (3%) |
| อ่านยอดได้ (หลังแก้) | **19/29 (66%)** |
| ความเร็วต่อใบ | 2-9 วินาที (SLO < 15s ✓) |

## บั๊กสำคัญที่เจอจากการวัดกับใบเสร็จจริง
1. **`SUBTOTAL` ถูกอ่านเป็นยอดรวม** — คำว่า `total` ซ่อนใน `subtotal`
   → ลูกค้าได้แต้มจากยอดก่อน VAT · แก้ด้วย word boundary + รายการคำต้องห้าม
2. **`Tota114900` → ยอด 900 บาท** (จริง 149) — regex ตัดเลขที่ติดกับตัวอักษรเป็นชิ้นๆ
   → แก้ให้ตัวเลขต้อง "ยืนเดี่ยว" · ผลคือระบบยอมบอก "อ่านไม่ได้" แทนการเดา
3. **OCR หั่นบรรทัดเดียวเป็นหลายกล่อง** — คำว่า total กับตัวเลขหลุดคนละกล่อง
   → รวมกล่องกลับเป็นบรรทัดด้วยการซ้อนทับแนวตั้ง
4. **เกณฑ์ความสว่างเข้มเกิน** (240) ตีกลับใบเสร็จที่ถ่ายมาดี — ใบเสร็จคือกระดาษขาว

## หลักที่ยึด
> **ให้แต้มผิด เสียหายกว่า ไม่ให้แต้ม**
> เมื่อไม่มั่นใจ ระบบต้องบอก "อ่านไม่ได้ ถ่ายใหม่" ไม่ใช่เดาตัวเลข
> (ครอบคลุมลดจาก 72% → 66% หลังแก้บั๊ก #2 — ยอมแลกเพราะ 72% นั้นมีเลขมั่วปนอยู่)
